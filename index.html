Funding Event Reconciliation Workbench

When a funding event fails, the truth is scattered across ACH return codes, bank-link state, event streams, and compliance review. This concept gives partner operations one recovery surface: classify what broke, route the owner, stage a human-approved next action, and show the MTTR it affects. ACH returns are one class of scenario inside a broader exception-observability product.

Discovery

The product thinking before the screens

A reconciliation tool is only credible if the discovery behind it is explicit. Persona, ranked pain, the job-to-be-done, the opportunity tree, and the metric are stated up front, then embodied in the workbench below.

Persona

Primary

Partner Money-Movement Operations Lead

Owns recovery when funding fails. Lives across ACH return codes, transfer-status events, partner DB state, Plaid bank-link evidence, compliance review, support messaging, and MTTR reporting.

Constraint Needs one operational truth fast — can’t stitch six tools per incident.

Secondary

Integration Developer

Needs to know whether local transfer status is still aligned with the source of truth when real-time event streams disconnect or a state transition is missed.

Pain points ranked

  1. No single recovery truth. High confidence

    When a funding event fails, “what broke / is retry safe / who owns next / what evidence / what metric degrades” lives across many systems.

  2. Return-code nuance is lost. Nacha R10/R11

    R10 (unauthorized) and R11 (authorization exists, terms mismatch) are not the same retry workflow. Treating them alike causes wrong actions.

  3. Event-stream gaps go silent. Assumption · to validate

    A missed SSE transfer event leaves partner state stale with no reconciliation trigger.

  4. MTTR isn’t instrumented per failure mode. Gap

    No per-exception MTTR, owner, or KPI view, so degradation is invisible until it’s large.

Job to be done

When a funding event fails (ACH return, missed event, instant-funding break), I want one place that tells me what broke, whether retry is safe, who owns the next step, what evidence is needed, what mock payload to stage, and what metric it affects, so I can recover fast without pretending to automate a regulated decision.

Riskiest assumption

That partner ops experience fragmented recovery truth as the top pain — not missing API primitives. The fastest way to invalidate this concept: if ops say the real gap is missing primitives, this targets the wrong layer.

Opportunity Solution Tree

Each opportunity maps to something you can see working below.

Desired outcome Reduce MTTR on funding-failure recovery without increasing wrong-action risk
  1. O1 Surface the right recovery context per return code
    • Scenario cards (R01/R03/R10/R11/SSE) carry risk, owner, KPI, runbook, and guardrail. See the Workbench
  2. O2 Make retry-safety an explicit, human-approved decision
    • auto_execute:false by default on regulated actions; the next step is a staged mock handoff, never an automatic one. See the case panel
  3. O3 Detect & reconcile event-stream gaps
    • A missed-event backfill scenario reconciles partner-local state from the REST source of truth, with an audit record. See “Missed transfer event”
  4. O4 Make degradation legible
    • Every scenario carries a metric-tree node and an MTTR target. See the Metric tree
